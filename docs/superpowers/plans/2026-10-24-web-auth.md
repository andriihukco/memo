# Web Auth and Profile Handles Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let users sign in to Memo on the web with email magic link, Google, or the Telegram Login Widget, pick a unique handle on first login, and link other providers from Settings.

**Architecture:** Supabase Auth user stays the primary identity (`profiles.id = auth.users.id`). A new `linked_identities` table maps each provider account to one profile. API routes accept either a Supabase Bearer JWT (the existing pattern) or a Supabase session cookie (new, for App Router pages). The Telegram Mini App `initData` flow is unchanged.

**Tech Stack:** Next.js 14 (App Router, edge runtime for existing auth route), `@supabase/supabase-js` 2.x, `@supabase/ssr` (new dependency), Vitest 4, Postgres via Supabase migrations.

**Spec:** [docs/superpowers/specs/2026-10-24-web-auth-design.md](../specs/2026-10-24-web-auth-design.md)

## Global Constraints

- Handle regex: `^[a-zA-Z0-9_]{3,20}$`.
- Handle change interval: 7 days (`604800` seconds).
- Telegram Login Widget `auth_date` max age: 86400 seconds.
- Providers: `email`, `google`, `telegram` only.
- Vercel login is out of scope.
- Handle uniqueness is case-insensitive (see Review Focus).
- Do not commit until the user says so. The branch `audit/p0-p1-fixes` has unrelated uncommitted work; each task's commit step stages only that task's files.

## Review Focus

1. **Handle case collisions.** `Alice` and `alice` must not both be claimable. Test: saving `Alice` when `alice` exists returns 409.
2. **Replayed Telegram Login Widget payload.** A payload older than 86400 seconds is rejected even with a valid hash. Test: `auth_date` 86401 seconds old → rejected.
3. **Linking an identity already linked to the same profile.** Returns 200 with no duplicate row. Test: second link call → 200, row count unchanged.
4. **Unlinking the last remaining sign-in method.** Refused with 409. Test: profile with one identity → DELETE returns 409.
5. **Telegram-only profile without a handle hitting bot-linked routes.** Bot routing still resolves by `linked_identities` provider `telegram`. Test: profile with `telegram_id` null and a `telegram` row → webhook resolves the profile.

### Task 1: Schema migration and backfill

**Files:**
- Create: `supabase/migrations/20240001000025_web_auth_identities.sql`

**Interfaces:**
- Consumes: existing `profiles(id, telegram_id, username)`.
- Produces: `profiles.handle`, `profiles.handle_changed_at`, table `linked_identities`. Later tasks rely on these exact column names.

- [ ] **Step 1: Write the migration**

```sql
ALTER TABLE profiles ALTER COLUMN telegram_id DROP NOT NULL;
ALTER TABLE profiles ADD COLUMN handle TEXT;
ALTER TABLE profiles ADD COLUMN handle_changed_at TIMESTAMPTZ;
ALTER TABLE profiles ADD CONSTRAINT profiles_handle_format
  CHECK (handle IS NULL OR handle ~ '^[a-zA-Z0-9_]{3,20}$');
CREATE UNIQUE INDEX profiles_handle_lower_key ON profiles (lower(handle)) WHERE handle IS NOT NULL;

CREATE TABLE linked_identities (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id           UUID NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
  provider          TEXT NOT NULL CHECK (provider IN ('email','google','telegram')),
  provider_user_id  TEXT NOT NULL,
  email             TEXT,
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (provider, provider_user_id)
);
CREATE INDEX linked_identities_user_id_idx ON linked_identities(user_id);

ALTER TABLE linked_identities ENABLE ROW LEVEL SECURITY;
CREATE POLICY linked_identities_select_own ON linked_identities
  FOR SELECT USING (user_id = auth.uid());
CREATE POLICY linked_identities_delete_own ON linked_identities
  FOR DELETE USING (user_id = auth.uid());

INSERT INTO linked_identities (user_id, provider, provider_user_id)
SELECT id, 'telegram', telegram_id::TEXT FROM profiles WHERE telegram_id IS NOT NULL
ON CONFLICT DO NOTHING;
```

The handle backfill is not in SQL. A profile's suggested handle depends on app-side validation, so Task 8 handles it on the user's first visit.

Expected: no errors. Then run `select count(*) from linked_identities where provider = 'telegram';` and compare with `select count(*) from profiles where telegram_id is not null;`. The counts must match.
